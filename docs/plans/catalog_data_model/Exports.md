# Export-market models

This is a proposal to add more structure around how the product represents models built for export to another market.

## Problem statement

Some pinball machine models are built specifically to serve a foreign market. They usually differ in `reward_type`: an add-a-ball or novelty edition of a replay/payout game, built for a jurisdiction that did not allow the original's reward type (Italy, France, Germany, Spain…).

Today the catalog represents this information in inconsistent ways:

- a dead `export` tag that is not used once, not a single time
- a `(Country)` suffix baked into the name
- freetext prose from IPDB in `extra_data` (not shown in the UI at all)
- and mostly not at all

We want to represent these relationships in a consistent, structured way, so that:

- We can see the inconsistencies and fix them
- It's difficult to see the export relationships in the UI, and we want to make those clear.
- For research purposes we can run queries and find export models

## Product Proposal

### 🆕 `export_edition_of`

Add a `MachineModel.export_edition_of` field to represent a model being an export edition of another model.

- This is a singular relationship — a model can only be an export edition of a single other model — so don’t try to represent this in the `ModelRelationships` join table.
- A model can set both `export_edition_of` **AND** other relationhsips, like `variant_of` or a `ModelRelationship` relationship type of `copy`. Usually but not always to the same target model.

### 🆕 model - location join table

Add a join table of model to location called `ModelExportMarket`.

- It's a join table because a model can be made for export to multiple countries / markets.
- There are TWO target fields `target_market_location` or `target_market_label`.
- The `target_market_location` can only be a country, i.e. Locations that have no parent.
- If we don’t know the country or if it's for export to a region like Europe and not a country, leave `target_market_location` blank.
- If it’s for export to a region like Europe and not a specific country, set `target_market_label` to something like “Europe”.
- This nullable target and model and textual label will work just like the `ModelRelationships` join table. Note that the text is not part of the identity, so a model cannot have a row with a blank label and another row with a filled out label. That’s good, that’s what we want.

### ❌ `export` tag

Delete the `export` tag. It exists as a `Tag` row (slug `export`) but has never been applied. Zero of our 6,915 models carry it. It's dead weight to retire alongside the composite tags in [ModelRelationships.md → step 9](ModelRelationships.md#migration-map).

## Data

Here's what the data says about export relationships.

### The table

The following table is a list of _candidate_ export-market models.

It was generated from two detectors:

- export-market phrasing in the IPDB free text (`extra_data.ipdb.notes`)
- models with a `(Country)` like `(Italy)` at the end of their names

These are _candidates_, not finished data:

- **It mixes export editions with their domestic originals.** Many rows are the _replay original_ (e.g. `Bank Shot`, `Ship Ahoy`, `King Pin`), caught only because their note names an export sibling ("The add-a-ball version for export to Italy is …"). Review flips those — the export edition is the _other_ model in the note. This is why the full `Note` excerpt is worth carrying, and why the count is a [noisy lower bound](#the-113-is-a-noisy-lower-bound).
- **`Likely origin` is a hint, not a resolution.** It is filled only from a structured lineage link or a confident note parse (`note?` marks a parse-derived guess); the authoritative origin comes from reading the note.

### Multi-destination

`Galaxie` was "made for export to Brazil then Italy" — two markets on one model. It is the only confirmed multi-destination case in the current data, but it settles the cardinality question: a single-valued FK would lose it. Export editions targeting a _region_ ("European export") do exist historically but never took a `(Country)` name and are out of scope here — this plan is about models built for one or more _identifiable_ markets, not the generic export production bucket (see [Not this](#not-this)).

### Lineage

Coverage of existing lineage across the full table: only **~6 of 113** carry any lineage link (FK or edge). The market fact and the lineage fact are both absent for ~95% of the candidates.

### Export is maker-relative

Whether serving a market counts as "export" depends on the maker's home. The notes carry both:

- `Grande Domino` — Gottlieb (USA), "made exclusively for the Italian market" → export (US → Italy).
- `Louisiana 2001` — a Belgian maker, "made for export to the United States" → export (Belgium → US).
- `Conquistador` — a Portuguese maker, art "designed in Portugal specifically for the Portuguese market" → **domestic**, not export, and a conversion of a Portuguese original — out of scope.

Consequence for the design: the stored fact is a _target market_ (a Location). "Export" — and the "for export to Italy" reader phrasing — is the derived case where the target market differs from the maker's home (or the origin machine's market). This is why the field name shouldn't hardcode "export" semantics that the display then has to walk back, and why seeding needs per-row judgment (`Conquistador` is a false positive the detector catches).

### The `(Country)` name suffix

In the free text notes that mentions export, only **4** of those models' names carry a country name-suffix. The rest were given their _own distinct names_ — `Card King` (export edition of `Pop-A-Card`), `Galaxie` (of `Dimension`), `Harmony` (of `Melody`), `Jungle Life`, `Elite Guard`, `Acapulco`, `Campidoglio`, … The `(Country)` suffix names ~4% of the phenomenon.

Exactly **11** models carry the suffix in total — **9 `(Italy)`, 2 `(Spain)`** (find them in the table above). It is pure disambiguation: it appears only when the maker reused the original's name (`Big Ben` / `Big Ben (Italy)`) and needed to tell the market edition apart from its sibling. 7 of the 11 aren't even caught by the free-text detector — their notes say "Italian add-a-ball model", not "export to" — which is exactly why the table unions both detectors.

### Export relationships between models: what shape are they?

Which market a model served is one axis (a model → `Location` fact). There is a second, independent axis: how the export edition relates to its **origin model**. Whether that lineage wants a new `export` relationship type, the existing `copy` type, or nothing new depends on what the origin relationships actually look like — so before deciding, here is what the data says. Four probes into the free-text core (the 106; the 7 suffix-only additions are all same-maker Italian add-a-ball variants — shape A — so they don't move these distributions).

**Probe 1 — the verb connecting the edition to its origin, in the note:**

| Connecting phrase                                                           | Models |

| "version of X" (unspecified)                                                | 14     |
| market-only (no origin machine named)                                       | 45     |
| explicit `copy of X`                                                        | 2      |
| `conversion of X`                                                           | 2      |
| other                                                                       | 10     |

#### The three shapes

The probes agree on three distinct relationship shapes, in descending frequency:

- **A. Same-maker reward-type variant (dominant).** ~60 same-maker origins, the 40/47 Add-a-Ball signature, and the reward-type-sibling phrasing all point at one thing: the maker — usually the original US maker — builds an add-a-ball or novelty edition of _its own_ replay/payout game for a market that restricted the original reward type. Same design, same maker, differs by reward configuration. In the domain model that is a [variant](../../DomainModel.md#title-model--variants), and it already is one on the ground: `Hurdy Gurdy (Italy)` carries `variant_of` → `Hurdy Gurdy`, and both sit in one Title (`Card Trix (Italy)` likewise shares its Title with `Card Trix`). This shape needs no copy edge and no export edge — it is a reward-type variant that also happens to carry a market.

- **B. Cross-maker copy (small tail).** A foreign licensee reproduces another maker's design on its own hardware, sometimes reward-shifted and then re-exported (`The Card` is a "near copy of Gottlieb's 1977 'Lucky Card' which was itself made for export to Italy"). This is a `copy` edge with a `license_status`, and it already works: `Big Ben (Italy)` (Segasa) carries `copy` → `Big Ben`. A handful of rows, not the population.

- **C. Standalone export build (large unlinked group).** ~38 name no origin machine and 56 are the sole model in their Title: games built for export with no distinct domestic sibling recorded, or whose sibling simply isn't linked. This shape carries no lineage edge at all — only the market fact.

### Does OPDB corroborate the variant classification?

Shape A calls these reward-type **variants**. OPDB is an independent authority with its own variant primitive, so it's worth asking whether it agrees. It has a three-level identity — `opdb_id` is `G<group>-M<machine>-A<alias>` — that maps cleanly onto ours: **group ≈ Title** (the family), **machine ≈ Model**, **alias ≈ `variant_of`** (a tight edition of one machine). If OPDB thought an export edition were a variant of the original, it would give it an **alias** (`-A…`) on the original's machine, exactly as it does for Pro/Premium/LE editions.

It almost never does. Across the 106:

| OPDB treatment of the export edition                    | Models |
| ------------------------------------------------------- | ------ |
| alias of a machine (`-A…`) — OPDB's own "variant of"    | **1**  |
| distinct machine (`-M…`) sharing a group with a sibling | 43     |
| distinct machine, alone in its OPDB group               | 10     |
| no `opdb_id` at all (OPDB has no record)                | 52     |

The lone alias is `Troubadour` (`GrPkZ-MW9K8-A96YD`), an alias of `Harmony` (`GrPkZ-MW9K8`) — and `Harmony` is itself a same-group **distinct machine** export edition of `Melody`, all Gottlieb. The prevailing pattern is `Card Trix (Italy)`: OPDB gives it its own machine (`GRWZN-MDv6X`) in the same group as `Card Trix` (`GRWZN-Mp41r`), not an alias of it.

So OPDB **does not** corroborate the tight `variant_of` reading; it corroborates the looser one. Its verdict is "a **distinct sibling model within the same family**" — the same thing [Probe 4](#export-relationships-between-models-what-shape-are-they)'s Title-sharing showed (OPDB group ≈ our Title), not "an edition of the original machine." (Our own data half-agrees: `Hurdy Gurdy (Italy)` — which OPDB _does_ alias, `GRpYQ-MdE3y-A1NZ3`, and which the freetext detector missed because its note says "Italian add-a-ball model" with no "export to" phrase — carries `variant_of` in our DB, while every other one carries nothing.)

This sharpens shape A rather than overturning it: the export edition is a same-maker, same-family, reward-shifted **sibling Model**. Whether the lineage is bound with an explicit `variant_of` FK (as `Hurdy Gurdy (Italy)` is) or left as an un-edged Title-sibling is a live modeling question — but both surfaces agree it belongs on the **family/variant** side, not the copy side, and neither needs a new export lineage type to say it.

### When does the edition share the original's Title — and is it the name?

The natural guess is that OPDB (and our catalog) split an edition into its own Title when it carries a **different name**. It's a correlate, not the rule. Across the 106, name-twinning vs Title-sharing:

|                                                       | shares a Title | own Title |
| ----------------------------------------------------- | -------------- | --------- |
| shares the original's name (e.g. `Card Trix (Italy)`) | 32             | 19        |
| unique name (e.g. `Harmony`)                          | 18             | 37        |

A shared name roughly doubles the odds of co-grouping (63% vs 33%) but is **neither necessary nor sufficient**: 18 _renamed_ editions still sit in their original's Title (`Harmony` in `Melody`'s Title _and_ OPDB group; `Galaxie`↔`Dimension`; `Grande Domino`↔`Domino`), and in the 44 OPDB-grouped cases **36 were grouped with only differently-named machines** — OPDB is plainly not keying on the string.

The real driver is the **maker**. Restricting to renamed editions (no name twin) and splitting by maker home:

| Renamed edition's maker                    | shares a Title | own Title |
| ------------------------------------------ | -------------- | --------- |
| same-territory (US) maker — its own family | 18             | 5         |
| foreign maker — a copy                     | **0**          | **32**    |

Every one of the 32 foreign-maker renamed editions is in its **own** Title; the same-maker renamed editions co-group 78% of the time. So the rule is: an edition shares the original's Title/group when it **reuses the name** (`Big Ben (Italy)`) _or_ is the **same maker's renamed edition** (`Harmony`); it takes its own Title only as a **foreign maker's renamed copy** (`Jungle Life` ← `Jungle King`). Name-difference and maker-difference are confounded — foreign copies almost always get a fresh name — and the clean 0/32 signal sits on the maker axis.

This lands exactly on the shape split above: **same-maker variant → shares the Title** (a sibling Model / OPDB group-mate), **cross-maker copy → own Title**. The Title/group structure already encodes the variant-vs-copy distinction, independent of naming — which is the same reason the market axis has to be modeled separately from it.

### What this says about `copy` vs a new `export` type

The market axis (which country) and the lineage axis (how it derives) are orthogonal, and the lineage axis is **already fully covered** by existing machinery: ~60 variants (`variant_of`), a few copies (`copy` edge), ~38 with no lineage at all. Nothing in the export data needs a lineage type the model doesn't have.

- **Reusing `copy` for the population would mis-model the majority.** `copy` is shape B — the minority. Shapes A and B carry _opposite_ [ordering/collapse behavior](ModelRelationships.md#relationship-type--a-code-enum-grown-by-release): `copy` is `subordinates=True` and, as a `variant_of`-null top-level model, a distinct machine that never heads its Title (the Big Ben rule); a reward-type variant collapses into its Title and does not subordinate. Modeling the ~60 same-maker editions as copies would push them below their Title head and list them as distinct machines instead of collapsing them — wrong on both the ordering and the collapse.
- **A new `export` relationship type would fuse the two axes and can't classify behavior.** Its members split across shapes A and B, which disagree on subordination — so the [exhaustiveness guard](ModelRelationships.md#relationship-type--a-code-enum-grown-by-release) would force one classification that is wrong for one group. And it would put "which country" (already `export_markets`) and "how derived" (already `variant_of`/`copy`) into the same field, the exact axis-fusion [that plan rejects for bootleg](ModelRelationships.md#derived-concepts-bootleg-and-licensed-build).

So the data-supported direction is to keep the two axes separate: represent the market as `export_markets` (the Location M2M), and leave the model → model edge as whatever it already is — `variant_of` for A, a `copy` edge for B, nothing for C. "The export edition of X" is then a _display_ phrasing derivable from (a variant/copy edge to X) + (non-empty `export_markets`), not a stored relationship type of its own.

## The 113 is a noisy lower bound

The detection is freetext pattern-matching over one source field (plus the name suffix) and needs human review before it becomes claims:

- **Under-counts.** Only reads `extra_data.ipdb.notes`; misses export facts stated only in `description`, in OPDB data, or with phrasing the patterns don't cover (e.g. "AAB" / add-a-ball edition naming with no market noun).
- **Over-counts.** Catches domestic "for the X market" notes where the maker _is_ from X (`Conquistador`), and — the biggest source — notes on the _domestic original_ that describe its export sibling ("the add-a-ball version for export to Italy is …"), which flag the original rather than the export edition (`Bank Shot`, `Ship Ahoy`, `King Pin` …). Review flips these to the sibling.

So 113 is the candidate list to review, not the answer. Treat seeding like the [ModelRelationships copy migration](ModelRelationships.md#why-the-mapping-must-be-applied-per-row-not-mechanically): per row, with the source in hand, never mechanical.

### The payoffs this unlocks

- **Structured query.** "All Italian export editions" becomes a join, not a name-substring guess that finds 4 of ~76.
- **Honest disambiguation.** The `(Italy)`/`(Spain)` naming hack retires: the name reverts to `Big Ben`, the fact moves to `export_markets = {Italy}`, and the UI renders "Big Ben _(for export to Italy)_" — or a badge — computed from data, with the market a `[[location:italy]]` wikilink.
- **Concept pages.** Feeds the [Articles](ModelRelationships.md#articles) follow-up directly — `[[article:italian_export_editions]]` over `export_markets` contains Italy, exactly parallel to the `italian_bootlegs` example.

```python
# full detection + destination parse (source of the counts above)
import json, re
from collections import Counter
from apps.catalog.models import MachineModel, Location

countries = set(Location.objects.filter(parent__isnull=True).values_list("name", flat=True)) | {"USA"}
adj = {"Italian": "Italy", "Spanish": "Spain", "French": "France", "German": "Germany",
       "Portuguese": "Portugal", "Japanese": "Japan", "Brazilian": "Brazil",
       "Belgian": "Belgium", "British": "United Kingdom", "American": "United States"}
rx_export = re.compile(r"export to (?:the\s+)?([A-Z][a-z]+(?:\s+[A-Z][a-z]+)*)")
rx_market = re.compile(r"for the ([A-Z][a-z]+) market")

population, dest_freq = {}, Counter()
for m in MachineModel.objects.exclude(extra_data="").iterator():
    try:
        notes = (json.loads(m.extra_data).get("ipdb.notes") or "")
    except (TypeError, ValueError):
        continue
    dests = set()
    for hit in rx_export.finditer(notes):
        cand = hit.group(1).strip()
        for c in countries:
            if cand == c or cand.startswith(c):
                dests.add("United States" if c in {"USA", "United States"} else c)
    for hit in rx_market.finditer(notes):
        a = hit.group(1)
        if a in adj:
            dests.add(adj[a])
        elif a in countries:
            dests.add(a)
    if dests:
        population[m.id] = (m.name, dests)
        for d in dests:
            dest_freq[d] += 1

print(len(population), "candidates")           # 106 (free text only)
print(dest_freq.most_common())                  # destination table
print([v for v in population.values() if len(v[1]) > 1])  # multi-destination: Galaxie
```

**Name vs maker as the Title-grouping driver.** `strip_edition` removes a trailing `(Country)`/`(AAB)` so `Card Trix (Italy)` twins with `Card Trix`:

```python
import re
from collections import Counter
from apps.catalog.models import MachineModel

def strip_edition(n):
    return re.sub(r"\s*\((?:Italy|Spain|France|Germany|AAB)\)\s*$", "", n, flags=re.I).strip().lower()

def root_country(m):  # climb Location parents to the country
    loc = m.corporate_entity.locations.first() if m.corporate_entity_id else None
    while loc and loc.parent_id:
        loc = loc.parent
    return loc.name if loc else None

pop = MachineModel.objects.filter(id__in=ids)               # the 106
title_size = Counter(MachineModel.objects.filter(
    title_id__in=pop.values_list("title_id", flat=True)).values_list("title_id", flat=True))

name_tab, maker_tab = Counter(), Counter()
for m in pop:
    twin = MachineModel.objects.exclude(id=m.id).filter(
        name__iexact=strip_edition(m.name)).exists() or MachineModel.objects.exclude(
        id=m.id).filter(name__iexact=m.name).exists()
    shares = m.title_id is not None and title_size[m.title_id] > 1
    name_tab[("twin" if twin else "unique", "shares" if shares else "own")] += 1
    if not twin:                                            # renamed only → maker split
        us = root_country(m) == "United States of America"
        maker_tab[("US" if us else "foreign", "shares" if shares else "own")] += 1

print(name_tab)   # twin/unique × shares/own Title  → 32 / 19 / 18 / 37
print(maker_tab)  # renamed only: US 18/5, foreign 0/32
```
