# Why the analytics layer returns confidently wrong answers

The recurring problem: an AI session needs information from the analytics foundation, writes a plausible query against `scripts/analysis/`, and gets a confidently wrong answer. This is not a complaint about difficulty — the queries are short and the domain is small. It is a complaint about a specific failure shape: **the wrong answer is syntactically valid, semantically plausible, numerically reasonable, and indistinguishable from a correct one.** Nothing errors. What unified most of the mechanisms below is a single line the layer drew without ever stating it: **it normalized structure and passed values through.** Liveness, foreign-key decoding, grain and fan-out were resolved for you. Absent-markers, identity encodings and JSON scalars were handed over exactly as Django stored them, so a query whose correctness depended on shape tended to be right while one whose correctness depended on what a value means tended to be wrong. All three value cases have since been fixed and the line is gone. What survives it is the more useful observation: erasing it took a different kind of fix each time, and the last one could not be found from inside SQL at all.

## What is NOT the problem

The domain model is not complicated and the view layer is not bloated. `catalog.sql` is ~1,400 lines of which 624 are comments: roughly 870 lines of SQL for 48 public views, about 18 lines each. Of the layer's 4,638 lines, ~42% is the self-test and ~25% is the claim-grain provenance and patch layers; the liveness-and-decode views that match the intuitive mental model are ~19%. Of nine documented instances of a wrong answer, one is attributable to genuine domain complexity (`model_edges` being outbound-only). The rest are produced by six mechanisms — the two still open below, plus four that have since been fixed and are summarized further down rather than restated. Instances and mechanisms are different units and one mechanism produces several instances, which is why the two counts do not reconcile and should not be made to.

Where the layer did normalize, it worked completely, and fan-out is the cleanest example: joining models to the raw `fc.catalog_machinemodel_themes` returns **9,974** rows against **6,938** models, silently inflating every count downstream, while the `themes` view carries a per-model list so the same join is 1:1 and the natural query is simply correct. Liveness is the same story — `WHERE status = 'active'` is catastrophically wrong against the raw table and does not need writing at all against `models`. That is the existence proof for the thesis above, and the reason this document is an argument about one specific omission rather than a general complaint.

## What IS the problem

The problems below are the distinct mechanisms that produce this.

### The mutation harness proves that checks fire, not that checks measure correctly

`check-mutations` breaks the catalog deliberately and asserts that the responsible check notices. It reported **131 mutations caught** while `_anchor_scan` was reporting one view's row counts for three others. That is not a harness failure — a check that fires on broken data can still be measuring the wrong thing — but it means the layer's strongest guarantee does not cover the failure class this document is about. Both defects found in this investigation were found by hand, by someone whose measurement contradicted an earlier measurement.

### A count whose unit is ambiguous is a wrong answer that looks like a right one

Every measure here reports a number, and a number carries no record of what it counted. `anchor_dark`'s measure was `live` — rows whose value is neither NULL nor the string `'0'` — which silently counted `''` as a value held, so one number conflated "this column holds something" with "this column holds something meaningful", and a 100%-blank column read as fully populated for the life of the mechanism. **This document then committed the same error about itself.** An enumeration of 66 subjects and an exemption list of 51 entries share the unit "entries", so they looked comparable, were compared, and yielded a conclusion neither supported; the writeup about confidently wrong answers carried one for three commits, and it took a reader who asked what was being counted rather than checking whether the counting was correct. It is the `''`-versus-NULL and `catalog.person` traps one level up — at the measure rather than the value, where the answer still looks like an answer. There is no fix beyond naming the unit, which is why `analysis columns` reports `n_rows`, `n_null` and `n_blank` as three columns rather than one fullness score. It is also the mechanism most likely to outlive every other fix here, because the reader produces it as readily as the layer does.

## What the fixes have in common, and what it cost to learn

Four of the mechanisms found in this investigation have been acted on, and none was fixed by adding a check. `''` versus NULL was fixed by a macro that folds absence to one spelling, so the wrong query stops being writable. A field no view exposed was fixed by `* EXCLUDE`, which gave a deliberate omission somewhere to be written down. The query engine returning wrong aggregates was fixed by importing the catalog instead of attaching it, which removed the class rather than detecting it. In each case the fix made the failure impossible or visible at the point of authoring; a check would have reported it later, to whoever happened to run the suite.

**The fourth is the one that had to leave SQL, and it is the most general.** `claims.subject_type` held `catalog.person`, not `person`, so `WHERE subject_type = 'person'` returned **0** rows against a true answer of **2,047** — and zero rows reads as a clean pass. What makes this different from the `''` case is that no amount of care inside the view layer could have produced the right spelling: `machinemodel` → `model` and `corporateentity` → `corporate-entity` are declarations on the Django model, not derivations, and SQL had no access to them. So the layer had done the only thing available to it, which was to restate the vocabulary in its own words — a hand-written 21-branch `UNION` whose header comment read "ADDING A CATALOG ENTITY MEANS ADDING A BRANCH", carried for the life of the view as a standing warning that it was a second source of truth. **Wherever this layer restates a fact the application already declares, the restatement is the defect, and the warning comment is the tell.** The fix generates both the vocabulary and the `UNION` from `LinkableModel` (`manage.py export_entity_registry`, `make codegen`), which respells the values, deletes the hand-list and retires the warning in one move. The Django spelling now survives in exactly one join predicate, where it is translated.

The pattern had one more instance, one view over, and how it was found is the point. `credits` derives its subject from a MachineModel-XOR-Series join, so it cannot inherit the value and spelled the two types itself. A reviewer probed it by renaming the vocabulary: `credits ⋈ claims USING (subject_type, subject_id)` fell from **426,614** rows to **21** — the Series half — silently, because a join returning too little still returns rows. Nothing in the suite noticed, and the reason is an asymmetry worth keeping. Every place that FILTERS on a subject type is loud when it goes stale: `model_claims` empties, and the agreement checks that consume it fire at 29,270 rows. Only EMISSION is silent, because a wrong value emitted is still a value, and every consumer downstream joins on it happily. **A restatement that feeds a predicate announces itself; a restatement that feeds a column does not.** It now reads `entity_type_of('catalog_machinemodel')`, keyed on the physical table because that is the handle that does not move when the vocabulary does.

The JSON half of the same mechanism was fixed the way `''` was — one spelling reaches a consumer — but it too could only be **found** by consulting the model. `production_quantity` is a `CharField`, which is what tells you that 2,784 claims storing `"500"` are the norm and 3 storing `500` are the anomaly rather than the reverse. 73 claims assert `production_quantity = 500`; `value = '500'` finds one, `value = '"500"'` finds 72, and neither query looks wrong. `claims.value_text` folds both, and it exposed a fact about the product rather than the layer: all four nonconforming claims are active and every one was written interactively, so the two write paths disagree about how to encode a scalar and nothing had ever been in a position to notice.

One bound on the claim. The fix makes the natural query correct; it does not make the unnatural one fail. A DuckDB `ENUM` over the vocabulary looked like it would turn `subject_type = 'catalog.person'` into a loud conversion error, and it does not — the comparison casts the enum back to `VARCHAR` and silently returns zero. So this rests entirely on the same argument the fan-out example makes, that the query a reader writes first is the one that is right, with nothing underneath to catch a reader who writes something else.

The attempts that failed are the useful part, and they failed for three different reasons that are easy to mistake for one. Pinning the `''` rule as a check — no public view column may hold `''` — needs one hand-written `UNION` branch per view, because `query_table()` accepts literals only and SQL cannot iterate relations, plus a meta-check to keep that enumeration honest. Its genuine exemptions number **one**: `citation_root_domains.path_prefix`, where `''` means "whole host". That obstacle is mechanical, not a failure to discriminate, and outside SQL it disappears — which is why the same measurement runs fine as a command. The text-based form — no view may carry a bare `fc.` reference — needs no iteration at all and catches an unwrapped join the data form misses, but **38 of 68 public views carry one**, because a semantic layer over an attached database reads that database; the predicate is aimed at the wrong thing. Only the third is the case the principle is about: `anchor_dark` asked whether a column was entirely empty and could not tell a broken join from a facet nobody has populated, which is irreducible variety in the population, and no reformulation removes it.

**At that size the exemption list stops being coverage and becomes the thing being maintained.** That is what retired the dark-anchor sweep, whose exemption list had reached 51 entries with six of its seven checks existing only to police it — and which was still short, since exposing physical columns by default made ten more all-empty columns visible that nobody had excused. The measurement was worth having; the gate around it was not, and it now runs as `analysis columns`, where `path_prefix` at 116 of 118 shows the difference in one line: a gate has to excuse it, a reader just reads the number.

The exemption count is the symptom, though, not the mechanism, and it is worth being precise about which. **A rule can gate when its predicate is derived from something the system already asserts structurally; it cannot gate when the predicate is a heuristic over a population that contains legitimate variety.** In that case the discrimination the predicate failed to make has to be hand-encoded instead, and the exemption list is where it goes. Counting entries is a fair **diagnosis of a rule already misbehaving** and a poor design-time test: it is silent on a rule with no exemptions yet, which is exactly when severity is hardest to call, and narrowing a rule's population makes exemptions vanish without the predicate improving at all. Ask the structural-versus-heuristic question directly; the count is the tripwire for a rule classified structural that turns out not to be. The contrast is visible in the same file: `entity_view_leaks_bookkeeping` keys on the derived lifecycle entity set, `models_has_deleted` compares a view against its own source, and the `live()` fixtures supply their own input — **zero exemptions between them**. `anchor_dark` asked whether a column was entirely empty, which cannot tell a broken join from a facet nobody has populated — 51. A corollary for anything built on this layer: severity belongs to the predicate, not to how bad the finding sounds. A rule whose predicate cannot separate a defect from legitimate variety is a worklist however serious its findings, because making it gate only moves the judgment into a list someone has to maintain.

## Open questions

Both value fixes normalize on the way out and leave the stored encoding alone, which settles the analytics question and not the backend one. Whether the _database_ should stop storing `''` for an unset field is still open. So is the sharper case the `value_text` work turned up: four active claims encode a scalar the way the other 2,900 on those fields do not, all four written interactively, so the interactive and ingest write paths disagree about a `CharField`. The layer can report that and cannot decide it — is it a bug in the write path or a shape the model permits?

Whether the two remaining mechanisms are one observation rather than two — that this layer verifies structure thoroughly and verifies measurement not at all. And whether the pattern above is a real principle or four cases that happened to rhyme; the fourth is the first that could not be fixed from inside SQL, which is either the strongest evidence for it or the point where it stops being one pattern.
