# Disentangle Claim Resolution from Catalog

## Context

Claim resolution materializes the catalog (denormalized columns + through-tables) from the claim log. The hard mechanical work already landed in [ClaimResolutionRefactor.md](../provenance/ClaimResolutionRefactor.md): `pick_winners`/`reconcile`/`Projection`/`ThroughRowProjection` are extracted into a catalog-free `_engine.py`, and the dispatch seam (`resolve_after_mutation`, `resolve_entities_bulk`, `ResolveHandlers`, `register_resolve_handlers`) already lives in `apps/provenance/resolution/`.

This effort is the next chapter: making the **whole** resolution boundary clean enough that extracting the rest from the catalog app could be done with `git mv`, the contracts are legible, and catalog can no longer leak into the generic machinery. The goal is the best system, not the most direct disentanglement.

The boundary is already mostly built. What remains:

1. **The relationship tier is not model-driven.** `resolve/_relationships.py` and `resolve/_dispatch.py` hand-write a projection _builder_ per namespace and hard-name ~15 concrete catalog models (`MachineModel`, `Credit`, `Theme`, …). pyproject.toml says so itself: _"the relationship/dispatch resolvers still bind MachineModel … it awaits the deferred relationship declaration vocabulary."_ This is the load-bearing entanglement — and a direct violation of the CLAUDE.md "catalog must be model-driven" rule for relationships.
2. **Contract hygiene.** One domain constant (`IMAGE_FIELDS`) sits in the would-be-generic core — deferred to POST4 (a hoist prerequisite, since it only bites when `_entities` actually moves to provenance), and preferably mooted by [the image→media promotion](../provenance/ClaimResolutionRefactor.md#POST3).

Scope is the **resolution layer only**; we aren't going to do a broad refactor of all of provenance here.

## <a id="related_docs"></a> Relation to adjacent work

This is the rung-4 model-driven relationship tier under the [ModelDrivenClaimResolution.md](../model_driven_metadata/ModelDrivenClaimResolution.md) umbrella vision: resolution lives in provenance, catalog declares its schema, and the dispatch table is computed from model metadata rather than hand-enumerated.

It builds directly on the registry [ProvenanceValidationTightening.md](../types/ProvenanceValidationTightening.md) shipped — `register_relationship_schema` / `RelationshipSchema` / `FkTarget` — which this work derives both the validation schema and the resolution projection from. Two pieces PVT scopes to the spec work land here: the identity-vs-`UniqueConstraint` cross-check (REF2) and `(namespace, subject_ct)` precision for shared namespaces (latent until value-key shapes diverge across subjects).

`claim_relationship_spec` follows the model-driven ClassVar pattern [ModelDrivenClaimsMetadata.md](../model_driven_metadata/ModelDrivenClaimsMetadata.md)'s `claim_fk_lookups` established — a per-model declaration on the model, consumed generically by shared infrastructure.

## Goals

1. **Stop the bleeding, both directions.** Import-linter ratchets so neither the generic resolution core imports catalog, nor provenance imports catalog.
2. **Model-driven relationship tier.** One declaration per relationship drives both validation schema and resolution projection; the generic builder names no concrete model.
3. **Clear, strongly-typed public contracts** to provenance and claim resolution — one import path per capability, no leaked privates.
4. **Clear, strongly-typed internal layer contracts** — write → rank → engine → dispatch → side-effect handlers, each a named typed seam.
5. **Easy to reason about** — one conceptual home per concept; "where does X live" has one answer.

**Success litmus:** the catalog-free resolution core can be `git mv`'d into `provenance/resolution/` with zero edits to the moved files. The move itself is POST5.

## What is already clean (do not redo)

- `_engine.py` (`reconcile`, `pick_winners`, `Projection`, `ThroughRowProjection`, converters) — catalog-free, import-linter-pinned.
- The provenance dispatch seam — `resolve_after_mutation`, `resolve_entities_bulk`, `ResolveHandlers`/`PerEntityResolver`/`BulkResolver`, `register_resolve_handlers`. Correct boundary; leave alone.
- `_entities.py`, `_helpers.py`, `_claim_values.py` — already fenced from catalog domain by the "Generic resolver core" contract.
- Side-effect placement: cache invalidation and markdown sync are correctly behind catalog's registered handlers / domain-neutral. The **only** domain impurity in the core is `IMAGE_FIELDS` (POST4).

## Design

### <a id="design-patterns"></a> Design patterns this builds on

The merge-and-materialize substrate this work configures is already named and single-sourced in ClaimResolutionRefactor.md — see [Design patterns & data structures](../provenance/ClaimResolutionRefactor.md#design-patterns) (desired-state reconciliation / the controller loop, materialized-view / IVM, the priority-ranked LWW register + tombstoned element-set merge, the `pick_winners` fold, level-triggered idempotence) and [The design](../provenance/ClaimResolutionRefactor.md#design) (the `reconcile` loop and the typed vocabulary — `Projection` / `Delta` / `MemberMap`, each `[Subject, Member, Payload]`, plus `RowState[Payload]` and `Winners[Subject, Group]`). This work reuses them unchanged; it does not restate them.

On top of that substrate it adds four constructs, named where they appear below:

- **Declarative spec + generic interpreter** — `build_through_projection` reads a typed `ClaimRelationshipSpec` and instantiates a configured `ThroughRowProjection` instead of a hand-written builder per namespace; this is rung 4 (declaration-derived dispatch) of [ModelDrivenClaimResolution.md](../model_driven_metadata/ModelDrivenClaimResolution.md)'s dispatch ladder.
- **Single source → derived twin registries** — one spec is mechanically projected into the validation schema and the resolution projection, neither a second source of truth.
- **Marker-base discovery** — `ClaimThroughModel` defines the universe of claim through-models so a missing spec fails loudly: a discovery ABC, not a shape taxonomy.
- **Closed-union dispatch** — `SubjectSpec` (`SingleSubject | XorSubject`) is a closed sum type; consumers branch on it with `match`/`case` plus a `case _: assert_never(...)` guard — the sanctioned alternative to `isinstance`-on-model branching, and the guard turns any future variant into a compile-time (mypy) failure rather than a silently unhandled case. (Self-referential parent hierarchies were expected to add a third `SelfParentSubject` variant; POST1 instead folds them into `SingleSubject` — child FK as subject, parent FK as identity member — so the union stays two-variant.)

### <a id="vocab"></a> The relationship declaration vocabulary (the centerpiece)

The 7 `ThroughRowProjection` builders in `_relationships.py` vary almost entirely by **data** — subject model, through model, key columns, payload column, FK-target validation sets, conflict policy — most of it Django-introspectable from the through-model. And the existing relationship-_schema_ registry's `ValueKeySpec(name, fk_target=…)` already declares the value-key→FK-target mapping that the resolution `extract` functions re-encode by hand. So one declaration can drive both.

Declare a pure-data spec as a `ClassVar` on each through-model (CLAUDE.md "base-class ClassVar → typed spec"); the spec **types** and the `ClaimThroughModel` marker base live in **`provenance/model_bases`**, beside `ClaimControlledModel` — the pinned "core-only leaf" (imports only `core`) that already holds the claim-control substrate every catalog model inherits, and is itself lift-out-ready. A relationship-_discovery_ registry is claim machinery, so it sits with the claim-control bases rather than in `core`; only the leaf _aliases_ the spec threads — `ClaimValueKey`/`IdentityPartName`/`ColumnName` — live in `core/types.py`. The spec stays domain-neutral (not pinball) and lift-out-ready, and every consumer imports _down_ into the leaf: catalog through-models already import their bases from `model_bases`, and the generic builder (in `provenance/resolution`) imports the spec from there too.

The dataclasses — `ClaimRelationshipSpec`, `SingleSubject`/`XorSubject` (`SubjectSpec`), `MemberField`, `PayloadField`, the `EmptyTargetPolicy`/`ScopePolicy` enums and the `ClaimThroughModel` marker base — live in `model_bases/claim_relationships.py` and `model_bases/models.py`; that code is the source of truth for their exact shapes. Two deliberate absences a reader won't infer from the code: `SubjectSpec` stays `SingleSubject | XorSubject` throughout — parents promote onto `SingleSubject` (POST1) rather than adding a variant, and until POST1 they ride the kept `_parent_projection`; and there is no `case_fold`/`display_member` field — aliases (the only case-folded shape) stay bespoke in REF and become generated-column through-rows in POST, so neither phase needs one.

A single generic `build_through_projection(binding: ClaimRelationshipBinding) -> ThroughRowProjection | None` reads the spec and configures `ThroughRowProjection`, reusing the `_engine.py` converters (`_int_from_column`, `_str_from_column`, `_int_or_none_from_column`, `_one_column`, … plus the compound-key `_compound_key`/`_compound_columns` added here for credit). Codecs are chosen by `len(members)`/`len(payload)`. Each FK member's `empty_target` policy decides what an empty target-PK set means: `DROP_INVALID` (the default — today's behavior for every namespace: members with invalid FKs are dropped) or `SKIP_NAMESPACE` (return `None`, skipping resolution so an unseeded vocabulary can't wipe existing rows). Only `Credit.role` is `SKIP_NAMESPACE`, reproducing today's sole guard; a blanket "any empty FK set → skip" would change behavior for credit's `person` and for theme/tag/location, so it stays opt-in per member. The `SubjectSpec` `match`/`case` (+ `case _: assert_never`) dispatch — the [closed-union dispatch](#design-patterns) construct, distinct from the `isinstance`-on-model smell the model-driven rule forbids — lives in `relationships_for`'s binding walk (REF1), **not** the builder: it resolves each subject FK into a `ClaimRelationshipBinding` carrying `subject_fk`/`subject_model`, so the builder derives `subject_column` directly and credit's XOR simply yields two bindings.

This is a declaration→executor split, **not** a second copy of the engine. The spec speaks **model-attribute** names (`field="theme"`); `ThroughRowProjection` (in `_engine.py`) speaks **DB columns + codecs** (`key_columns=("theme_id",)`); `build_through_projection` is the single bridge — it derives columns from `_meta` and selects codecs from `_engine`'s converters, so the spec never restates a column or codec the engine already owns. The redundancy the spec retires lives in `_relationships.py`, not `_engine.py`: `M2MFieldSpec`/`M2M_FIELDS` is a hand-maintained partial precursor of `ClaimRelationshipSpec`, and the per-shape `_*_projection` builders are its hand-written lowering — both deleted in REF4. `_engine.py`'s through-row machinery (`ThroughRowProjection`, the converters, `reconcile`) is generic and stays.

Whether a member is an FK (validated against a target-PK set) or a literal string is **introspected** from `through_model._meta.get_field(field)` — the spec carries no model-class reference, so it stays a pure ClassVar with no import-order or circular-import hazard (`Credit.role` uses the string FK `"CreditRole"` for exactly this reason). The validation schema's `FkTarget` (for write-time existence checks) is built catalog-side during the `ready()` derivation (REF4) as `FkTarget(<target introspected from `\_meta.get_field(member.field).related_model`>, member.lookup_field)`, where importing it from `provenance.validation` is allowed; `provenance.resolution` never imports it, keeping the two same-layer siblings uncoupled. `lookup_field` defaults to `"pk"` (every current spec) and is the only consumer of that `MemberField` field — resolution keys on the resolved target pk directly, so it never reads `lookup_field`.

Credit (compound key) and ModelAbbreviation fit the generic builder: the XOR subject resolves via `subject_column` selection plus `ThroughRowProjection.read`'s NULL-subject exclusion, and a model's abbreviations resolve claim-locally. Three shapes don't flow through the generic ClassVar path in REF — two ride transitional paths that POST retires, one is irreducible:

- **Parent hierarchies** (`theme_parent` / `gameplay_feature_parent`) — self-referential M2Ms whose implicit `.through` carries no ClassVar. REF keeps today's `_parent_projection` (synthesized from `.through`, the `from_/to_` convention; `scope=FULL_TYPE`). The **POST parent-promotion** step makes them explicit ClassVar through-models — declared as `SingleSubject("from_<model>")` with the parent FK as the identity member, no new union variant — and deletes `_parent_projection`.
- **`AliasProjection`** — case-folded key ≠ stored display (keyed by `value.lower()`, value kept in original case), so not a `ThroughRowProjection`. REF keeps it **as-is**, on its own `discover_alias_types()` channel (not the `ClaimThroughModel` walk — `AliasModel`s are flat FK rows, not through-models), `scope=FULL_TYPE`. The **POST alias-normalization** step adds a `value_normalized` `GeneratedField`, making aliases plain ClassVar through-rows (`key = value_normalized`, `payload = value`) and deleting `AliasProjection` — no `case_fold`/`display_member` spec field ever needed, since the DB maintains the normalized key.
- **`MediaProjection`** — content-type-keyed, imports `apps.media.models`, and is **irreducibly** bespoke (no POST step folds it in): (1) its projection is invoked through catalog's existing per-model handler / `resolve_media_attachments`, **not** an independent registration — the per-model `ResolveHandlers` seam allows one pair per model and catalog (ahead of media in `INSTALLED_APPS`) owns it, so a multi-provider seam would be required and is out of scope. The `MediaProjection` _class_ **stays catalog-side** (`catalog/resolve/_media.py`): it imports provenance ranking/models, the engine and catalog's cache, whereas media is peer-isolated from provenance (only the `MediaSupportedModel` base edge is sanctioned) and its `exhaustive` internal stack has no resolution tier — so media can't host it without a new boundary. media owns only the `EntityMedia`/`MediaAsset` target tables. (2) Its validation schema + per-entity category check are registered by the existing `MediaSupportedModel` walk, **not** derived from a `ClaimThroughModel` — media materializes into the polymorphic `EntityMedia`, which has no per-pair through-model to carry a spec.

So REF's generic builder covers the explicit ClassVar shapes; parents and aliases ride transitional paths, and after the two POST polish steps only `MediaProjection` remains bespoke. (`media_attachment`'s schema escape-hatch is independent — see REF4.)

### One declaration, two derived registries

Catalog's `ready()` keeps the inversion (provenance never imports catalog): walk `ClaimThroughModel` subclasses + `discover_alias_types()`, then derive the two registries off the one declaration — but at **different cardinality**, because the validation registry is namespace-keyed while resolution is per-through-model:

- **(a) Validation schemas — spec→schema is many-to-one.** Group specs by `namespace`, then derive one `RelationshipSchema` per namespace: union `valid_subjects` across the group, and assert value-key shape and bound parity across the members (reproducing today's cross-model agreement check — e.g. `abbreviation` spans `ModelAbbreviation` + `TitleAbbreviation` and asserts equal `max_length`; `credit`'s `XorSubject` yields `valid_subjects={MachineModel, Series}`). Harvest `max_length`/`min_value` from `_meta` exactly as `claims.py` does today, then call the **unchanged** `register_relationship_schema(...)` once per namespace. A naive per-spec registration would conflict — the registry raises on a second, differing schema for the same namespace.
- **(b) Resolution projections — per `(namespace, subject)`.** Build the resolution registry from the same walk with `build_through_projection` partial-applied instead of hand-written fns.

Do **not** merge the two runtime registries (different keys, different cardinality) — they share the _declaration_ and the _walk_, not the cache. A consistency test locks each representation: spec → `RelationshipSchema` (`test_through_model_schemas`) and spec → projection ctor args (`test_through_projection`). The through-model namespaces no longer carry a `_claim_values.py` TypedDict — only the three bespoke payload shapes remain, mirror-checked by `test_claim_values`.

### <a id="read_surface"></a> One public read surface, and its consumers

The spec registry lives in **`provenance/model_bases`** (beside `ClaimControlledModel`) and is populated by a lazy `ClaimThroughModel` walk over the app registry — so it imports no catalog (`model_bases` is core-only-pinned). It ships **two** public queries over the one cached index (`_ensure_bindings`): `relationships_for(model)` for a single subject's bindings, and `all_relationship_bindings()` for the flat set the REF4 derivations iterate. Each binding pairs a spec with its through-model, subject model, subject FK and live reverse/M2M accessor, and every consumer calls those, never a private `_meta` re-walk or a second registry. Coverage boundary: because it walks `ClaimThroughModel` subclasses, in REF it returns the explicit ClassVar through-model specs only — **not** parents (synthesized via `_parent_projection`), aliases (bespoke), or media. The two POST polish steps fold parents and aliases into the walk; media stays out. So a consumer wanting _every_ claim relationship combines `relationships_for` with the still-outside paths — `discover_alias_types()` + the media walk in REF, media alone post-POST. This is the "single source, derived cache" discipline of the validation/resolution twins extended to the query surface: it is what stops the third and fourth consumer each growing a hand-maintained copy.

Most existing consumers read the **derived schema** and need no change once it is spec-derived (REF4): `provenance.claims.build_relationship_claim` (canonical identity keys), `provenance.display` (identity/payload rendering incl. `display_key`), `claim_ingest`'s patch-emit shapes, and the per-subject namespace sets the post-apply adapter reads. The read surface is for consumers needing **spec-level** facts the schema doesn't carry (through-model, accessor, shape).

**In scope here:** the read surface itself, plus the two derivations that exercise it (validation schema + resolution projection, REF4).

**Enabled, but out of this plan's resolution-layer scope** — listed so the next consumer adopts the surface instead of re-walking; each then becomes a one-spec edit rather than a second hand-edit:

- `catalog/api/export.py` — `ExportSpec.relations` already filters `get_all_relationship_schemas()` by `valid_subjects` (`export.py:289`) but still hand-lists `_rel("themes", "slugs")` / `_rel("abbreviations", "strings")` / `_rel("credits", …)`. Both halves are derivable: the **accessor** is the reverse/M2M whose `.through` is the spec's through-model; the **shape** is `"slugs"` (FK member) / `"strings"` (literal member) / `"credits"` (compound). Only genuine overrides — prefetch hints, the credit person+role serialization — stay hand-written.
- Backend relationship **edit planners** (aliases, abbreviations, parents, M2M, credits) — claim-shape construction should ride the same declaration; UI layout stays model-specific.
- Frontend relationship-editor metadata — generate from the declaration if generic edit forms grow, rather than hand-maintained TS unions.
- Entity metadata's `relationships` field — adopt only if it means _claim-controlled_ relationships; if it's navigation/display, derive a narrower projection or keep it separate.

### Why the spec is pure data

The spec carries **no resolver callable** — resolution behavior lives in `resolve/` (the generic builder + the `AliasProjection` builder), keyed off the spec. A resolver on the model would invert the dependency (models importing resolver code that imports models) and erode the spec's cohesion as a pure declaration; pure data also keeps codegen for non-Python consumers open.

#### Alternatives rejected

Alternatives weighed and rejected:

- **ABC-as-shape-taxonomy** (`EntityRefClaim`/`LiteralClaim`/`RelationshipClaim` subclasses with shape-enforcing abstract methods). A data object validates the same shapes at `ready()`; several through-models straddle categories; a class taxonomy locks in a hierarchy future claim shapes will fight. (`ClaimThroughModel` is _discovery only_ — no abstract methods — a different, kept decision.)
- **A hand-maintained consolidated registry** as the canonical declaration (what `ProvenanceValidationTightening.md` shipped as the interim). Better than scattered registries, but the declaration still lives away from the model and the registry accrues dumping-ground pressure. The derived design makes the spec a model ClassVar `ready()` picks up mechanically — the registry becomes a derived cache, not a second source of truth.

The resolution semantics themselves — winner-per-`(object_id, claim_key)` by priority then recency, `exists=false` tombstones, the `is_active` + `source.is_enabled` pre-filter, idempotent diff, subject scoping — are already implemented and single-sourced in `_engine.py` / `ranked_claims` / `member_is_present` (see [ClaimResolutionRefactor.md's invariants](../provenance/ClaimResolutionRefactor.md#invariants-to-preserve)); this work does not change them.

### <a id="internal_layers"></a> Internal layers

Five layers; the first four already typed and clean. The only new seam is the `ExtraDataHook` registry (POST4, deferred to the hoist) that evicts `IMAGE_FIELDS` from the core. Cache (behind handlers) and markdown sync (domain-neutral, `apps.core.markdown`) need no new protocol.

#### ✅ DONE: <a id="REF3">REF3</a> — Generic `build_through_projection`

Landed. The generic builder lives in the new catalog-free module `apps/catalog/resolve/_through_projection.py` — `build_through_projection(binding) -> ThroughRowProjection | None` drives entirely off `binding.spec` + `through_model._meta`, names no concrete model (imports only `_engine` + `provenance.model_bases`), so it joins the would-be-movable resolution core. It takes a `ClaimRelationshipBinding`, not the originally-sketched `(subject_model, through_model)`: REF1's binding gained a `subject_fk` field this branch (which also retired the throwaway `SubjectAccessor`, building bindings directly), so the builder derives `subject_column` and resolves which credit XOR branch a binding occupies with no re-introspection, and credit×2 falls out of the two bindings. Compound (credit) keys use two new generic `_engine` converters — `_compound_key`/`_compound_columns` (identity on the column tuple) — so credit's `Member` is a plain tuple rather than the bespoke `CreditAssignment` NamedTuple (equal to it; the member type is internal, only column values persist). The extractor collapses the hand-written builders' three null/type guards into one strictest policy (tolerate a null `claim.value`, require an `int` present in the target-PK set per FK member, drop a literal only when missing); the single-payload codec is narrowed to the one extant int shape behind a _type_-checked guard that raises `NotImplementedError` on any other payload, so a future string/decimal `PayloadField` fails loudly instead of silently mis-converting.

Behavior-preserving: the builder is **not yet wired into dispatch** — the hand-written `_*_projection` builders still drive resolution, and `_parent_projection`/`AliasProjection` stay untouched (REF4 wires the builder in and deletes the hand-written ones). The equivalence suite (`apps/catalog/resolve/tests/test_through_projection.py`) is REF3's whole proof: identical data ctor args + the _same_ `_engine` converter objects for the eight scalar shapes (`is`), the compound-codec round-trip for credit, `extract` equivalence on valid claims, matching invalid-PK / bool-PK / null-value drops (with the documented production-unreachable divergences — only location's hand-written builder tolerates a null value; the rest raise), `SKIP_NAMESPACE` vs `DROP_INVALID` build behavior, a completeness guard that the cases are exactly what `relationships_for` yields, and end-to-end `reconcile` byte-identity (the generic materializes, is idempotent, then the hand-written builder sees its rows as already-desired).

### <a id="POST"></a> POST — uniformity polish, ratchets, de-domaining, and the move

#### ✅ DONE: <a id="POST1">POST1</a> — Promote parent hierarchies to explicit through-models

Landed. `Theme.parents`/`GameplayFeature.parents` are now the explicit `ThemeParent`/`GameplayFeatureParent` through-models (`apps/catalog/models/{theme,gameplay_feature}.py`), declared as `SingleSubject("from_<model>")` with the parent FK as a `value_key="parent"` identity member. **No `SubjectSpec` variant was added** — a parent edge is just subject-FK + member-FK, which `SingleSubject` already expresses, so the binding walk and `checks.py` uniqueness dispatch handle it unchanged (the originally-sketched `SelfParentSubject` was dropped as redundant; the design-patterns and vocabulary sections above were revised to match). The M2M is repointed at the through (`through=`/`through_fields=`) to keep `parents`/`children` prefetchable, and the through is pinned to the auto-M2M's table/columns/CASCADE/`unique_together`, so migration `0016_promote_parent_through_models` is a `SeparateDatabaseAndState` with empty `database_operations` (zero DDL). Schema and projection now derive from the spec via the REF4 walk; `_parent_projection`, its dispatch entry, the hand-written `theme_parent`/`gameplay_feature_parent` registration in `claims.py` and the `ParentClaimValue` TypedDict are gone. Behavior-preserving — the derived schema is byte-identical to the deleted hand-written one. See the models, `0016`, and the parent cases in `resolve/tests/test_through_{projection,model_schemas}.py` + `tests/test_migration_parent_promotion.py` for the details.

#### <a id="POST2">POST2</a> — Normalize aliases into plain through-rows

REF keeps the bespoke `AliasProjection` (case-folded key ≠ stored display). Replace it with a model change: add a `value_normalized` `GeneratedField(expression=Lower("value"), db_persist=True)` to each alias model (`ThemeAlias`, `GameplayFeatureAlias`, `ManufacturerAlias`, …) with a unique constraint on the normalized key — **field-based** (`UniqueConstraint(fields=["value_normalized"])` or `unique=True` on the field), not an expression UC like `Lower("value")`: the REF2 check matches identity against `UniqueConstraint.fields`, which is empty for expression constraints, so once these alias models become `ClaimThroughModel`s their identity UC must be a plain field constraint. Works on prod Postgres and dev SQLite alike (Django 6 + SQLite 3.50; SQLite rebuilds the table to add a STORED generated column, invisible and a non-issue for resettable dev DBs). The DB maintains the normalized key, so aliases become plain ClassVar through-rows (`key = value_normalized`, `payload = value` in original case) declared on the alias models (now `ClaimThroughModel`s), folding into the generic builder; `AliasProjection` and the `discover_alias_types()` resolution path are deleted, and `normalize_alias_identity` stops splitting value/display (the claim carries original-case `value`; the DB derives the key). Displayed output is unchanged — a storage refactor. **Verify first:** the alias `display` override must be a case/whitespace variant of the identity value, so `lower(value)` reproduces the dedup key; if `display` can differ arbitrarily, store the identity source as its own column rather than deriving it. A data-model change beyond the resolution layer, hence POST; it pairs with POST1 to leave only `MediaProjection` bespoke.

POST2 also deletes the REF2 system check's `provenance.E004` (`identity == value_key`) and its two tests: aliases are the first `identity != value_key` case (`identity="alias"` vs value key `"alias_value"`), so folding them into the `ClaimThroughModel` walk retires the convention E004 enforces. (REF4 kept E004 because no spec violated it yet.)

#### <a id="POST3">POST3</a> — Import-linter ratchets, both directions

- **`provenance ⊄ catalog`**: add a forbidden contract `source_modules = ["apps.provenance"]`, `forbidden_modules = ["apps.catalog"]` (with test `ignore_imports`). provenance carries no production import of catalog, so the contract holds as written.
- **Generic resolver core ⊄ catalog** (after REF): today there are **two** catalog-free contracts — "Resolution engine primitives stay catalog-free" (`_engine` only, forbids all of `apps.catalog`) and "Generic resolver core does not import the catalog domain" (`_entities`/`_helpers`/`_claim_values`, forbids an enumerated subset). Reconcile them into **one** coherent movable-set contract: `source_modules` = the full movable set (`_engine`, `build_through_projection`, the `_image_fields` machinery, `_entities`, `_helpers`), `forbidden_modules = ["apps.catalog", …]` matching the `_engine` pattern. (`_image_fields` is import-clean today, so it joins the movable set here even though its conceptual de-domaining is deferred to POST4; the `model_bases`-resident spec types + `ClaimThroughModel` are already barred from catalog by the "Claim-control bases stay a core-only leaf" contract, so they need no movable-set entry. `_claim_values` is dropped from the set — it is import-free but pinball-_shaped_ payload vocabulary, catalog's, not generic; see REF4.)

#### <a id="POST4">POST4</a> — Evict `IMAGE_FIELDS` from the generic core (hoist prerequisite)

`IMAGE_FIELDS = {"opdb.images", "ipdb.image_urls", "image_urls"}` in `_image_fields.py` is pinball/source-domain knowledge in the otherwise-generic scalar core, stamped during `_apply_claims`. It is import-clean today (so it does not block the POST3 ratchet), but becomes a **conceptual** leak the moment `_entities` — which calls the stamp — moves to provenance, so the de-domaining is sequenced here, immediately before the POST5 hoist, as that move's one prerequisite. **Preferably mooted entirely** by [ClaimResolutionRefactor.md POST3](../provenance/ClaimResolutionRefactor.md#POST3)'s image→media promotion, which deletes `_image_fields` outright — deletion over abstraction; do the hook inversion below only if the hoist is undertaken before that lands.

The inversion: an `ExtraDataHook` registry in the **movable resolver core** (beside `_image_fields`/`_entities`, **not** `apps.core` — it threads provenance license context and is consumed only by `_apply_claims`, so it travels with the core on the hoist) — `register_extra_data_hook(field_name, hook)`, where `hook: (extra_data: JsonBody, claim: Claim, sfl_map: SourceFieldLicenseMap | None) -> None` (all core/provenance types: `JsonBody` from `core.types`, `Claim`/`SourceFieldLicenseMap` from provenance). The stamp helper's body is generic license denormalization; only the field→hook mapping is domain knowledge, so catalog registers the stamp for each image field at `CatalogConfig.ready()` (~3 lines) and `IMAGE_FIELDS` moves catalog-side. `_apply_claims` loses the `IMAGE_FIELDS` import and calls registered hooks; the `sfl_map` pre-build guard generalizes from "field ∈ `IMAGE_FIELDS`" to "field has a registered hook." Behavior-preserving — byte-identical sidecars.

#### <a id="POST5">POST5</a> — Hoist the catalog-free core into `provenance/resolution/`

Keep the core **whole** as the `provenance/resolution/` package (it already is a cohesive multi-module subsystem beside the dispatch seam — do not scatter it into provenance root modules): with `_image_fields` de-domained by POST4, `git mv` `{_engine, build_through_projection, dispatch registry mechanism, _helpers, _entities, _image_fields machinery}` in (the spec types + `ClaimThroughModel` already live in `provenance/model_bases`; `_claim_values` is pinball payload vocabulary and stays catalog-side; `AliasProjection`/`_parent_projection` were deleted by POST1–POST2 — so none move), and restate the catalog-free contract one app down as the intra-provenance form (`apps.provenance.resolution ⊄ apps.catalog`). The catalog remainder (`_dispatch` registration, the spec-walk, side-effect handlers) keeps registering at `CatalogConfig.ready()` and imports the moved core from `apps.provenance.resolution.*`.
